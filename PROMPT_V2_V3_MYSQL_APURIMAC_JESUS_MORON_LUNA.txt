============================================================ 3.
TECNOLOGÍAS OBLIGATORIAS Y DECISIONES
============================================================

Utiliza:

-   Frontend: el React existente.
-   Lenguaje frontend: conservar JavaScript o TypeScript según el
    proyecto existente.
-   Backend: Node.js.
-   Framework backend: Express.
-   API: REST en JSON.
-   Base de datos: MySQL.
-   Comunicación frontend/backend: conservar fetch o axios si ya se usa;
    si no, escoger una opción y centralizar las peticiones.
-   CORS configurado para el origen del frontend.
-   Variables de entorno para credenciales y configuración.
-   Un driver u ORM compatible con MySQL.

Para acceso a datos, inspecciona primero las dependencias. Si no existe
una elección previa, puedes usar Prisma con el proveedor MySQL o mysql2
con consultas parametrizadas. Escoge UNA estrategia coherente; no
mezcles herramientas de acceso a datos innecesariamente.

Si utilizas Prisma, configura explícitamente MySQL como proveedor y
genera las migraciones correspondientes. Si utilizas mysql2, crea
scripts SQL versionados y documenta cómo ejecutarlos.

No cambies la base de datos a otra tecnología.

============================================================ 4. ¿DEBES
CREAR TÚ LA BASE DE DATOS?
============================================================

Sí: debes preparar e implementar todo lo que se pueda desde el
repositorio para que la base de datos MySQL quede lista para utilizarse.

Esto incluye: - diseñar el modelo relacional; - crear las tablas y
relaciones necesarias; - definir claves primarias y foráneas; - definir
índices y restricciones; - crear migraciones o scripts SQL; - crear un

del backend a MySQL; - crear .env.example; - documentar comandos de
instalación y ejecución; - comprobar la conexión cuando exista una
instancia MySQL disponible.

Si tienes acceso real a una instancia MySQL configurada, crea/aplica las
migraciones y verifica las tablas. Si no tienes acceso al servidor, no
finjas que la base de datos quedó creada o conectada: deja el esquema,
las migraciones y el seed listos, y explícame exactamente qué debo hacer
yo en MySQL para crear la base y proporcionar las credenciales.

No inventes ni adivines contraseñas, host, usuario o credenciales. No
sobrescribas una base existente ni ejecutes operaciones destructivas sin
verificar el entorno y el contenido.

Usa un nombre claro para la base, por ejemplo apurimac_turismo, salvo
que el proyecto ya tenga un nombre establecido.

============================================================ 6. MODELO
RELACIONAL MYSQL
============================================================

Define el esquema real a partir de las pantallas y formularios
existentes. No crees tablas por suposición si la interfaz no utiliza esa
funcionalidad.

Como mínimo, considera las entidades siguientes cuando correspondan:

A. users - id. - nombre. - apellido, si se utiliza. - email único. -
password_hash. - role, por ejemplo ADMIN o USER. - estado
activo/inactivo si hace falta. - created_at y updated_at.

B. destinations - id. - nombre. - slug único. - ubicación. -
descripción. - imagen principal. - categoría si aplica. - estado
publicado/borrador. - timestamps.

C. experiences - id. - nombre. - slug único. - destino relacionado
mediante clave foránea cuando corresponda. - descripción corta y
completa. - categoría. - duración. - dificultad, si aplica. - precio
referencial. - qué incluye y qué no incluye. - imágenes. - estado
publicado/borrador. - timestamps.

D. accommodations - id. - nombre. - slug único. - destino/ubicación. -
descripción. - tipo de alojamiento. - precio por noche. - capacidad. -
servicios. - imágenes. - estado publicado/borrador. - timestamps.

E. reservations - id. - código único de reserva. - usuario asociado si
hay cuenta. - datos de contacto necesarios para reservas como invitado,
si esa es la lógica actual. - experiencia y/o alojamiento
seleccionados. - fecha de llegada y salida o fecha de experiencia según
corresponda. - número de personas. - precio unitario y total calculado
por el backend. - estado de reserva. - estado de pago, sin afirmar que
hubo un pago real. - observaciones. - timestamps.

F. Otras entidades: Solo agregar testimonios, categorías, galerías,
habitaciones u otras tablas si el frontend existente o las reglas de
negocio las necesitan.

REQUISITOS DEL ESQUEMA: - Usa tipos adecuados de MySQL. - Define claves
primarias y foráneas. - Define restricciones UNIQUE donde
correspondan. - Define índices para búsquedas frecuentes. - Usa DECIMAL
para importes monetarios; no uses FLOAT para precios. - Define reglas de
borrado/actualización coherentes. - Evita duplicar datos
innecesariamente. - Documenta las relaciones. - Usa migraciones
versionadas. - Respeta el motor y versión de MySQL disponible en el
entorno.

Si una reserva puede incluir tanto una experiencia como un hospedaje,
diseña esa relación de manera consistente y calcula el importe sin
duplicidades.

no contradice el proyecto.

Ejemplos de recursos públicos: - GET /api/v1/destinations - GET
/api/v1/destinations/:idOrSlug - GET /api/v1/experiences - GET
/api/v1/experiences/:idOrSlug - GET /api/v1/accommodations - GET
/api/v1/accommodations/:idOrSlug - POST /api/v1/reservations

/api/v1/auth/register - POST /api/v1/auth/login - POST
/api/v1/auth/logout - GET /api/v1/auth/me

GET /api/v1/my/reservations/:id - PATCH
/api/v1/my/reservations/:id/cancel

Administración: - CRUD /api/v1/admin/destinations - CRUD
/api/v1/admin/experiences - CRUD /api/v1/admin/accommodations - CRUD
/api/v1/admin/reservations - CRUD de otras entidades administrables que
ya existan. - Gestión de usuarios solo si corresponde y con permisos
estrictos.

Estos endpoints son una guía: adáptalos a los recursos reales.
Implementa los métodos GET, POST, PUT/PATCH y DELETE que correspondan.

Incluye: - códigos HTTP correctos; - validación de parámetros y body; -
respuestas JSON coherentes; - manejo centralizado de errores; -
paginación/filtros si son necesarios; - consultas parametrizadas o
ORM; - mensajes sin datos sensibles; - nunca devolver password_hash.

============================================================ 10.
AUTENTICACIÓN, ROLES Y CONTRASEÑAS
============================================================

Implementa autenticación básica segura, según el flujo que tenga el
proyecto.

Requisitos: - inicio de sesión; - cierre de sesión; - consulta del
usuario actual; - registro solo si existe en el alcance; - roles como
ADMIN y USER cuando correspondan; - hash de contraseñas mediante bcrypt
o bcryptjs; - middleware de autenticación; - middleware de
autorización; - endpoints administrativos protegidos; - validación de
datos; - respuestas genéricas para credenciales incorrectas.

Usa una estrategia coherente de sesión o JWT. Preferir cookies HttpOnly
y seguras en producción cuando la arquitectura lo permita. Si usas JWT
en cookies, considera las medidas necesarias para CSRF y CORS. No
guardes contraseñas en texto plano ni expongas tokens o secretos.

No codifiques una contraseña de administrador fija en el repositorio.
Prepara un seed o procedimiento seguro para crear el primer admin
leyendo credenciales desde variables de entorno. No imprimas la
contraseña en logs.
